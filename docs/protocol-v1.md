# Спецификация TCP Protocol v1

Сетевой протокол прикладного уровня, разработанный для системы резервного копирования файлов. Протокол функционирует поверх TCP-сокетов с гарантированной доставкой и ориентацией на непрерывный поток байт.

---

## 1. Физическая структура кадра (Physical Frame)

Каждый пакет данных передается в виде кадра следующего формата:

```
+------------------------------------+--------------------------+-----------------------+
|  4 байта (UInt32 Big-Endian)       |  HeaderLength байт       |  BodyLength байт      |
|  Длина заголовка (HeaderLength)    |  UTF-8 JSON Заголовок    |  Тело (Body stream)   |
+------------------------------------+--------------------------+-----------------------+
```

### Поля кадра:
1. **HeaderLength (4 байта):** Беззнаковое 32-битное целое число в сетевом порядке байт (**Big-Endian**), определяющее точный размер JSON-заголовка в байтах.
2. **JSON Header (`HeaderLength` байт):** Сериализованный в кодировке UTF-8 объект метаданных кадра.
3. **Body (`BodyLength` байт):** Произвольные бинарные данные или JSON-полезная нагрузка. Длина определяется полем `BodyLength` из заголовка. Если `BodyLength == 0`, тело в кадре отсутствует.

---

## 2. Ограничения и валидация

- **Максимальный размер заголовка:** строго **не более 64 KiB** (65 536 байт). При получении `HeaderLength > 65536` или `HeaderLength == 0` соединение немедленно разрывается с генерацией `ProtocolException`.
- **Порядок байт:** Длина заголовка всегда кодируется в Big-Endian (`BinaryPrimitives.WriteUInt32BigEndian`).
- **Фрагментация TCP:** Прием данных выполняется через циклическое накопление (`ReadExactlyAsync`), исключающее предположение о том, что один вызов `NetworkStream.ReadAsync` вернет весь кадр целиком.
- **Потоковая передача (Streaming):** Для `BodyLength > 0` чтение и запись могут осуществляться блоками (чанками по 64 KiB) напрямую в/из файлового потока, что защищает от переполнения оперативной памяти при передаче многогигабайтных архивов.

## 3. Структура JSON-заголовка (`ProtocolHeader`)

Заголовок представляет собой JSON-документ следующего формата:

```json
{
  "magic": "BKP1",
  "protocolVersion": 1,
  "messageType": "Hello",
  "messageId": "c5f59045-8fd1-477c-a496-e131d575792d",
  "correlationId": null,
  "contentType": "application/json",
  "bodyLength": 45,
  "sentAtUtc": "2026-10-07T14:30:00.1234567Z"
}
```

### Спецификация полей заголовка:

| Поле | Тип | Описание | Обязательность |
| :--- | :--- | :--- | :--- |
| `magic` | String | Константа `"BKP1"`. Защита от случайных подключений. | Обязательно |
| `protocolVersion` | Int32 | Версия протокола (на текущем этапе — `1`). | Обязательно |
| `messageType` | String / Enum | Тип передаваемого сообщения из каталога протокола. | Обязательно |
| `messageId` | Guid | Уникальный идентификатор конкретного сообщения. | Обязательно |
| `correlationId` | Guid? (nullable) | ID исходного запроса. Заполняется в ответе для связывания запроса и ответа. | Опционально |
| `contentType` | String | MIME-тип полезной нагрузки: `"application/json"`, `"application/octet-stream"`. | Обязательно |
| `bodyLength` | Int64 | Длина тела в байтах (целое неотрицательное число $\ge 0$). | Обязательно |
| `sentAtUtc` | DateTime (ISO-8601) | Время отправки сообщения в формате UTC. | Обязательно |

---

## 4. Каталог типов сообщений (`MessageType`)

В контракте Protocol v1 зафиксирован полный набор типов сообщений распределенной системы:

### Системные и диагностические:
- `Hello`: Рукопожатие клиента с сервером при установлении соединения.
- `HelloAck`: Подтверждение рукопожатия и готовности сервера.
- `Ping`: Проверка жизнеспособности соединения (heartbeat).
- `Pong`: Ответ на ping.
- `Error`: Сообщение о протокольной или системной ошибке.

### Сессия синхронизации и план изменений:
- `Manifest`: Передача локального снимка файлов клиента на сервер.
- `SyncPlan`: Расчетный план синхронизации (какие файлы загрузить, удалить или переименовать).
- `SyncCompleted`: Уведомление об успешном завершении полного цикла синхронизации.

### События файловой системы:
- `FileCreated`: Событие создания файла в отслеживаемой директории.
- `FileChanged`: Событие изменения содержимого или метаданных файла.
- `FileDeleted`: Событие удаления файла.
- `FileRenamed`: Событие переименования или перемещения файла.

### Загрузка данных в хранилище:
- `UploadRequired`: Запрос подтверждения необходимости загрузки файла.
- `UploadFile`: Потоковая передача содержимого файла в хранилище.
- `UploadCompleted`: Подтверждение успешной загрузки файла.

### Запросы метаданных и истории версий:
- `GetFiles`: Запрос списка файлов в репозитории.
- `FilesResponse`: Ответ со списком файлов и актуальными состояниями.
- `GetVersions`: Запрос истории версий конкретного файла.
- `VersionsResponse`: Ответ с журналом версий файла.

### Восстановление файлов (Restore):
- `RestoreRequest`: Запрос восстановления версии файла.
- `RestoreFile`: Потоковая отдача файла из хранилища клиенту.
- `RestoreCompleted`: Завершение операции восстановления.

### Внутреннее взаимодействие шлюза с сервисом метаданных:
- `PrepareVersion`: Подготовка транзакции создания новой версии в БД.
- `PrepareVersionResult`: Результат подготовки версии.
- `CommitVersion`: Фиксация версии и журнала изменений.
- `CommitVersionResult`: Результат фиксации версии.
- `DeleteFileMetadata`: Пометка файла удаленным в метаданных.
- `RenameFileMetadata`: Обновление пути файла в метаданных.
- `ResolveVersion`: Запрос актуального хэша и метаданных файла.
- `ResolveVersionResult`: Результат разрешения версии.

### Внутреннее взаимодействие шлюза с сервисом хранилища:
- `StoreFile`: Запрос на запись физического файла в хранилище.
- `StoreFileResult`: Результат сохранения файла.
- `GetStoredFile`: Запрос на чтение физического файла из хранилища.
- `StoredFile`: Потоковый ответ с телом запрашиваемого файла.

## 5. Примеры базовых сценариев обмена

### Сценарий 1: Рукопожатие (Handshake)

1. **Клиент -> Сервер:**
   - Кадр:
     - HeaderLength: `148` байт
     - Header:
       ```json
       {
         "magic": "BKP1",
         "protocolVersion": 1,
         "messageType": "Hello",
         "messageId": "a1b2c3d4-e5f6-7890-abcd-ef1234567890",
         "correlationId": null,
         "contentType": "application/json",
         "bodyLength": 42,
         "sentAtUtc": "2026-10-07T14:30:00.000Z"
       }
       ```
     - Body:
       ```json
       {
         "clientName": "Backup.SyncGateway",
         "version": "1.0"
       }
       ```

2. **Сервер -> Клиент:**
   - Кадр:
     - HeaderLength: `185` байт
     - Header:
       ```json
       {
         "magic": "BKP1",
         "protocolVersion": 1,
         "messageType": "HelloAck",
         "messageId": "98765432-dcba-0987-6543-21fedcba0987",
         "correlationId": "a1b2c3d4-e5f6-7890-abcd-ef1234567890",
         "contentType": "application/json",
         "bodyLength": 76,
         "sentAtUtc": "2026-10-07T14:30:00.015Z"
       }
       ```
     - Body:
       ```json
       {
         "serverName": "Backup.MetadataService",
         "version": "1.0",
         "success": true,
         "message": "MetadataService is ready."
       }
       ```

---

### Сценарий 2: Проверка активности (Ping / Pong)

1. **Клиент -> Сервер:**
   - Header: `messageType: "Ping"`, `bodyLength: 25`, `messageId: "..."`
   - Body: `{"timestamp": 1791383400000}`
2. **Сервер -> Клиент:**
   - Header: `messageType: "Pong"`, `correlationId: "<id исходного Ping>"`, `bodyLength: 25`
   - Body: `{"timestamp": 1791383400005}`
